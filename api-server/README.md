# OpenReview API

Hono + Better Auth + Drizzle + PostgreSQL on Cloudflare Workers. This package is
`api-server/` in the existing monorepo; `frontend/` (SolidJS) and `landing-page/`
(Astro) are unchanged. No Node HTTP server or separate auth service is used.

## Local setup

Use Node 24 LTS and npm. From `api-server/`:

```sh
npm ci
cp .dev.vars.example .dev.vars
```

Edit `.dev.vars`: supply a **local/development** database, local GitHub App OAuth
credentials, a random Better Auth secret (at least 32 characters), and a separate
random webhook secret. For example, generate secrets with
`openssl rand -base64 32`. Never commit these values.

```sh
npm run db:migrate
npm run dev
```

Wrangler serves `http://localhost:1337`. Start the existing frontend separately on
`http://localhost:5173`. `/health` is a liveness check, not a database readiness check.
An unauthenticated `GET /api/v1/me` returns 401 once configuration is valid.

`.dev.vars` is the supported local configuration file. Wrangler does not merge
`.env` into it. Drizzle tooling also reads `.dev.vars`; an explicitly supplied
process environment takes precedence. The pre-existing `.env` and `.env.example`
were not rewritten. Migrate any old `GITHUB_CLIENT_SECRECT` / `WEBHOOK_SECRECT`
names to `GITHUB_CLIENT_SECRET` / `GITHUB_WEBHOOK_SECRET`. Neither `WEBHOOK_URL`
nor `GITHUB_WEBHOOK_URL` is required.

## Configuration

| Binding / variable      | Purpose                                                                  |
| ----------------------- | ------------------------------------------------------------------------ |
| `ENVIRONMENT`           | `local`, `dev`, or `production`, set in Wrangler                         |
| `BETTER_AUTH_URL`       | Exact API origin (no path or trailing slash)                             |
| `FRONTEND_URL`          | Single explicit trusted frontend origin                                  |
| `BETTER_AUTH_SECRET`    | Secret signing sessions and encrypting provider tokens                   |
| `GITHUB_CLIENT_ID`      | Environment-specific GitHub App OAuth client ID                          |
| `GITHUB_CLIENT_SECRET`  | Environment-specific GitHub App OAuth secret                             |
| `GITHUB_WEBHOOK_SECRET` | Reserved secret for future ingestion; not used to acknowledge events yet |
| `DATABASE_URL`          | Local runtime and direct migration connection, never a frontend variable |
| `HYPERDRIVE`            | Required database binding in deployed environments                       |

| Environment | API                             | Frontend                    | GitHub authorization callback                            |
| ----------- | ------------------------------- | --------------------------- | -------------------------------------------------------- |
| Local       | `http://localhost:1337`         | `http://localhost:5173`     | `http://localhost:1337/api/auth/callback/github`         |
| Dev         | `https://api.dev.openreview.si` | `https://dev.openreview.si` | `https://api.dev.openreview.si/api/auth/callback/github` |
| Production  | `https://api.openreview.si`     | `https://openreview.si`     | `https://api.openreview.si/api/auth/callback/github`     |

Use separate GitHub Apps/OAuth credentials, auth secrets, webhook secrets,
databases, and Hyperdrive configurations for all three environments. Separate
databases are the supported isolation strategy here; do not point dev at production.
The origins are deliberately validated against the selected environment.

Secrets belong in Cloudflare-managed secrets for deployments. `DATABASE_URL` is
not used as a fallback in deployed environments, even if accidentally present.
No backend secret belongs in a `VITE_*` variable.

## Database and schema workflow

`src/db/auth-schema.ts` is generated by the **matching Better Auth CLI** from the
same options/plugins used at runtime. It includes organizations and teams. Do not
hand-maintain a second authentication schema.

```sh
npm run auth:generate
npm run db:generate
npm run db:migrate
```

Generation does not require credentials or a database connection. Inspect and
commit generated schema and SQL changes. Drizzle Kit applies SQL migrations
explicitly; the Worker never migrates on startup. Do not use Better Auth's direct
`migrate` command with this Drizzle-managed schema.

Initial migration: `drizzle/0000_free_supernaut.sql` plus Drizzle metadata.
Tables: `user`, `session`, `account`, `verification`, `organization`, `member`,
`invitation`, `team`, `team_member`. Account identities are provider-neutral:
`provider_id` and stable `account_id`, with a foreign key to the internal user.

Application tables belong in `src/db/schema.ts`. None are needed in this phase.

For a confirmed development database, use a separately protected environment file:

```sh
DB_ENV_FILE=.dev.vars.dev npm run db:migrate
```

That file must contain the **direct dev database** `DATABASE_URL`; Hyperdrive
bindings cannot be used by the migration CLI outside a Worker. Review the target
before running. Production migrations require a separately authorized rollout.

Runtime pools are lazy, scoped to one request, capped at one connection, bounded
by timeouts, and closed in `finally`. Hyperdrive supplies the distributed origin
pool. No auth instances or database connections are cached across requests.

## GitHub App settings and tokens

Set the authorization callback from the table above in each environment's GitHub
App. Enable **Account permissions → Email addresses → Read-only**, including
approval of any changed permissions by existing users. Better Auth requests
`read:user` and `user:email`; a usable email is required by its user schema.
Display name and avatar are mapped by the provider; usernames are not identity keys.

Better Auth handles OAuth state, code exchange, linked accounts, and sessions.
Implicit email-based linking is disabled; future providers can be linked explicitly
by signed-in users with `linkSocial`. GitLab OAuth is not configured yet.

The installed GitHub provider supports refresh tokens from expiring GitHub App
user tokens. Better Auth stores token expiration fields and encrypted access and
refresh tokens, and its server-side `getAccessToken` API can refresh when needed.
Do not assume a valid OpenReview session means the GitHub token is valid. Future
integration code must handle expiration, revoked consent and refresh failures,
and request reauthorization when necessary. Refresh is not a scheduled background
task. Repository browsing now uses that backend-only provider integration; see
[GitHub dashboard API](docs/GITHUB_API.md).

HTTP `/api/auth/get-access-token` and `/api/auth/refresh-token` are disabled to keep
provider tokens out of browsers. Never return account rows from application APIs.
GitHub App installation tokens are a separate future integration, not login tokens.
Protect and back up `BETTER_AUTH_SECRET`; changing it without a rotation plan can
invalidate sessions and make existing encrypted provider tokens unreadable.

## SolidJS browser integration (no frontend rewrite)

Install `better-auth` in `frontend/` when integrating it, then create a browser client:

```ts
import { createAuthClient } from "better-auth/solid";
import { organizationClient } from "better-auth/client/plugins";

export const authClient = createAuthClient({
  baseURL: "http://localhost:1337", // use the matching API origin when deployed
  fetchOptions: { credentials: "include" },
  plugins: [organizationClient({ teams: { enabled: true } })],
});

await authClient.signIn.social({
  provider: "github",
  callbackURL: new URL("/dashboard", window.location.origin).href,
});
```

Use the **absolute frontend callback URL**: a relative `/dashboard` can resolve on
the API origin instead. After GitHub redirects to the dashboard, test:

```ts
await authClient.getSession();
await fetch("http://localhost:1337/api/v1/me", { credentials: "include" });
await authClient.organization.create({
  name: "My workspace",
  slug: "my-workspace",
});
await authClient.organization.list();
await authClient.organization.setActive({ organizationId: "..." });
await authClient.organization.inviteMember({
  email: "developer@example.com",
  role: "member",
});
await authClient.organization.listUserInvitations();
await authClient.organization.acceptInvitation({ invitationId: "..." });
await authClient.organization.rejectInvitation({ invitationId: "..." });
await authClient.organization.listMembers({ query: { organizationId: "..." } });
await authClient.organization.removeMember({
  memberIdOrEmail: "...",
  organizationId: "...",
});
await authClient.organization.update({
  data: { name: "New name" },
  organizationId: "...",
});
await authClient.organization.leave({ organizationId: "..." });
await authClient.signOut();
```

The organization plugin owns roles (`owner`, `admin`, `member`), permissions,
invitations, teams, last-owner protection, and membership changes. Internal
OpenReview workspaces are **not** GitHub organizations. There is no automatic
workspace creation or GitHub organization import at login.

Invitations persist and verified recipients can discover them using
`listUserInvitations` and accept/reject them while signed in with the matching
email. **Invitation email delivery is not configured.** Add a real
`sendInvitationEmail` implementation when a delivery provider is selected; no
email delivery is claimed and no invitation links are logged.

Cookies are HttpOnly, host-only, SameSite=Lax and Secure on HTTPS. Local ports
share the same site; deployed frontend/API pairs also share a site, so domain-wide
cookies or SameSite=None are unnecessary. Use `localhost` consistently, not a mix
of `localhost` and `127.0.0.1`. Browser requests must include credentials. Origin
checks and Better Auth CSRF protection remain enabled. CORS never uses `*`.

## Routes and authorization

- `GET /` — preserved starter route
- `GET /health` — public liveness, no database query
- `GET /api/v1` — public API information
- `/api/auth/*` — official Better Auth handler, including all organization APIs
- `GET /api/v1/me` — authenticated, allowlisted user fields only
- `GET /api/v1/me/organizations` — authenticated membership-scoped list
- `GET /api/v1/github/connection` — GitHub identity and installation status
- `GET /api/v1/repositories` — paginated, installation-scoped repositories
- `GET /api/v1/pull-requests` — repository-specific or combined ordered PR list
- `GET /api/v1/dashboard/overview` — accessible repository/PR counts and recent PRs
- `GET /api/v1/repositories/:repositoryId/pull-requests/:number` — PR detail
- `GET /api/v1/repositories/:repositoryId/pull-requests/:number/files` — paginated files
- `GET /api/v1/github/install` and `/install/callback` — user/browser-bound installation flow
- `POST /api/v1/webhooks/github` — signature-verified review ingestion; requires review setup
- `GET|POST /api/v1/repositories/:repositoryId/reviews/settings` — per-repository review switch (admin); default on
- `GET|POST /api/v1/repositories/:repositoryId/pull-requests/:number/reviews` — history/request/retry

The reusable `requireAuth` middleware validates through Better Auth, attaches
typed user/session context, and forwards refreshed session cookies. Organization
listing reuses the validated user rather than querying the session twice. Future
resource routes must call `requireOrganizationPermission` after authentication;
it checks actual membership and delegates permissions to Better Auth. Never
authorize using a supplied ID or `activeOrganizationId` alone.

Errors do not expose database messages, tokens or environment values. Auth and
database logs deliberately contain no provider payloads. Configure Cloudflare
WAF/rate limiting for public authentication endpoints before public rollout;
per-isolate memory rate limits are not a distributed abuse-control mechanism.

## Hyperdrive and deployment

No infrastructure has been provisioned by this change. In the Cloudflare dashboard,
create independent Hyperdrive configurations for the dev and production databases
and **disable query caching**. Cached auth/session/membership reads can make logout
or permission revocation ineffective. Use TLS with certificate validation for the
origin connection, where supported by your database provider.

Equivalent Wrangler command templates (run manually with protected credentials;
connection-string arguments can be visible in process lists):

```sh
npx wrangler hyperdrive create openreview-dev --connection-string='<DEV_DIRECT_DATABASE_URL>' --caching-disabled --env dev
npx wrangler hyperdrive create openreview-production --connection-string='<PRODUCTION_DIRECT_DATABASE_URL>' --caching-disabled --env production
```

Prefer the dashboard to enter credentials without putting them in shell arguments.
For existing configurations, `npx wrangler hyperdrive update <ID> --caching-disabled`.
Take the real IDs returned by Cloudflare and uncomment/configure the corresponding
`hyperdrive` entries under **each** environment in `wrangler.jsonc`. The commented
placeholders are not usable bindings. Then regenerate types:

```sh
npm run cf-typegen
```

Use interactive secrets commands with distinct values for each target:

```sh
npx wrangler secret put BETTER_AUTH_SECRET --env dev
npx wrangler secret put GITHUB_CLIENT_ID --env dev
npx wrangler secret put GITHUB_CLIENT_SECRET --env dev
npx wrangler secret put GITHUB_WEBHOOK_SECRET --env dev
```

Repeat with `--env production` **only during an authorized production rollout**.
Wrangler secret commands can deploy new Worker versions. Local secret files are
not uploaded automatically. Confirm Cloudflare account, domain/zone ownership,
Hyperdrive binding, database target and OAuth app before deploying:

```sh
npm run typecheck
npm test
npm run build
npx wrangler deploy --dry-run --env dev
npm run deploy:dev
# Only after explicit production approval:
npm run deploy:prod
```

`wrangler.jsonc` retains compatibility date `2026-10-23`, explicitly enables
`nodejs_compat`, and enables logs/traces. Custom domains are configured separately
for dev and production; `workers.dev` is disabled for those environments.

## Checks and limitations

```sh
npm run test:integration  # real Better Auth + Drizzle + disposable PGlite
npm run test:workers      # actual Workers runtime smoke tests
npm run typecheck
npm run build            # packaging only, no deployment
npm run format           # Prettier 4.0.0-alpha.13, package-wide formatting
npm run format:check
```

Tests use no GitHub credentials. The SQL migration is executed against disposable
PGlite storage in integration tests. This verifies PostgreSQL-compatible schema,
sessions and authorization, **not** a real origin PostgreSQL/Hyperdrive connection
or GitHub authorization callback exchange. Run a real browser login, migration
and revocation check against your confirmed development database before rollout.

The initial environment has no Better Auth secret or confirmed non-production
database designation. No existing database was migrated, no Hyperdrive resource
was created, and nothing was deployed. Real login and live database connectivity
remain credential/infrastructure-dependent setup steps.

`npm audit` currently reports four moderate development-tool dependency findings
through Drizzle Kit's legacy esbuild loader. The suggested forced downgrade is
incompatible with this setup; it has not been applied. Avoid exposing development
tool servers to untrusted networks and review upstream fixes.

## Future persistent provider integration migration

Keep identity accounts separate from repository authorization. Live repository
browsing requires no new tables. When durable workspace connections and background
synchronization are implemented, add application-owned tables such as:

- `provider_connection`: internal organization FK, provider (`github`/`gitlab`),
  external account ID, nullable installation ID, connection status, timestamps;
  scope external identifiers by provider and document installation ownership.
- `provider_repository`: connection FK, stable external repository ID, display
  name/path, timestamps; unique by connection + external ID.

Use text for external IDs, not JavaScript numbers. Authorize via internal workspace
membership. GitHub organizations/GitLab groups can supply many connections to one
workspace; they never replace internal workspace ownership. Defer exact uniqueness
and transfer rules until durable workspace installation linking is implemented.

Code reviews now have signature-verified webhook ingestion, PostgreSQL-backed
deduplication/jobs, a Cloudflare Queue consumer, recovery dispatch, installation
tokens, bounded OpenAI analysis, GitHub COMMENT reviews, and dashboard results.
Automatic reviews run by default for every installed repository once
credentials, database and queue are configured; administrators can disable them
per repository, and there is no global enable flag.
See [docs/CODE_REVIEWS.md](docs/CODE_REVIEWS.md) before enabling deliveries. The new
migration has been generated, not applied; queues have not been provisioned or
deployed. Persistent repository synchronization and GitLab OAuth remain deferred.

The read-only GitHub dashboard APIs and installation setup flow are documented in
[docs/GITHUB_API.md](docs/GITHUB_API.md), including the additional `GITHUB_APP_SLUG`
configuration, GitHub App permissions, separate Setup URL, frontend examples,
pagination behavior, and bounded live-query limits. Successful GitHub reads now
use an encrypted, user-/account-/token-scoped Workers cache for at most 30 seconds.
GitHub-side access revocations can therefore take up to 30 seconds to appear;
OpenReview session and linked-account checks still run on every request. Explicit
Refresh bypasses the cache. Cold requests still wait for GitHub. Local authenticated
API reads and cache hits were verified without changing GitHub App settings.

Formatting uses the pinned Prettier 4 prerelease, not a globally installed v3.
Secret files, build output, dependencies, generated Wrangler declarations,
Drizzle snapshots and the npm lockfile are excluded by `.prettierignore`.
